# HerdHarbor Alpha v1.8.4 Stability Release Contract

## Purpose

Alpha v1.8.4 is a controlled production-stability release built on the current Alpha v1.8.3 production baseline. It is not a major feature release.

The release exists to finish hardening the systems already introduced or consolidated in v1.8.3:

- normalized cloud-sync rollout safety and reversibility
- cloud-sync resilience and provider-failure observability
- production telemetry validation
- cross-device and lifecycle/state-integrity protection
- PWA/service-worker/update reliability
- authentication regression protection
- subscription/payment-state reliability
- end-to-end connected-workflow regression coverage
- release/test documentation cleanup

## Scope boundary

PR 1 changes release contracts, documentation, and regression assertions only. It must not:

- enable normalized sync for new production cohorts
- enable percentage rollout
- remove legacy recovery data
- change authentication architecture or signup policy
- alter subscription policy
- introduce destructive production validation
- expose member/farm/animal payloads, credentials, tokens, or secrets
- rename stable historical engine/component files merely to say v1.8.4
- merge automatically

## AI boundary

v1.8.4 does not expand AI functionality. Existing v1.8.3 AI-assisted behavior remains frozen except for a verified stability/security defect. New or expanded Paper Pedigree AI, photo-assisted AI entry, voice-assisted AI entry, and other AI-assisted workflows are roadmap work for v2.0.1.

## Version ownership

Whole-application release identity and component/engine build identity are separate contracts.

During PRs 1-8, the whole-app release remains v1.8.3 unless the repository's established release process proves an earlier change is required. Stable component filenames and independent build IDs remain unchanged unless their owning component actually changes.

The formal whole-app promotion to Alpha v1.8.4 belongs to PR 9 after the preceding stability stack is complete and green.

Each phase branches from the final head of the immediately previous phase. Later phases must not branch from main. No phase is auto-merged.

## Go / no-go criteria

A phase is GO only when:

- its branch is based on the required parent head
- its owned tests/checks pass
- broader regression gates required by that phase pass
- no security/privacy/auth/sync/state-integrity assertion was weakened to get green
- production behavior changes, if any, are explicitly documented
- rollback requirements are documented and feasible
- the stack ledger is updated with exact base/head/test evidence

A phase is NO-GO when any release blocker below remains unresolved.

## Release blockers

- unresolved data-loss or silent-deletion path
- unresolved stale-client overwrite path
- normalized rollout without verified schema/preflight/RLS/RPC/rollback evidence
- cloud telemetry that loses provider/runtime provenance or leaks private payloads
- auth startup/callback/session regression
- service-worker/PWA update path that can strand users on an invalid shell
- subscription transition that can destructively downgrade or delete stored herd data
- failing required CI/regression/security/privacy gate
- unexplained main divergence that invalidates stack ancestry
- destructive or unreviewed production migration requirement

## Rollback requirements

- normalized sync: adjacent rollback only (`normalized -> dual_write -> shadow -> legacy`) with legacy recovery retained
- application/runtime changes: revert the owning phase without deleting canonical user data
- PWA/service worker: preserve a valid prior shell/update path and deterministic cache cleanup
- auth/subscription: restore last known-good behavior without changing stored farm data
- operator-only production actions: document exact reversal/stop procedure; do not simulate them in browser startup
