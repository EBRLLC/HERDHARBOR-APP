# HerdHarbor Alpha v1.6.1 — Crash Monitoring Setup

> Phase 1 only: stability, crash/error diagnostics, privacy-safe observability, and monitoring infrastructure.
>
> **DO NOT MERGE / DO NOT DEPLOY until explicitly approved.** This document does not implement memberships, subscriptions, pricing, paywalls, trials, RevenueCat, StoreKit billing, or Google Play Billing.

## 1. Architecture

HerdHarbor Alpha v1.6.1 uses one centralized JavaScript monitoring layer built around `@sentry/browser`.

Primary files:

- `monitoring/herdharbor-monitoring-core.mjs` — central service, tagging, deduplication, safe capture APIs, global exception/rejection handlers, Cloud Sync and spreadsheet adapters.
- `monitoring/herdharbor-monitoring-browser.mjs` — Browser SDK bootstrap.
- `monitoring/herdharbor-monitoring-privacy.mjs` — final outbound-event hardening and breadcrumb filtering.
- `monitoring/herdharbor-monitoring-instrumentation.mjs` — value-blind localStorage/IndexedDB failure hooks and explicit feature breadcrumbs.
- `herdharbor-monitoring-config.js` — runtime configuration. The committed copy always has a blank DSN.
- `scripts/build-monitoring.mjs` — bundles `@sentry/browser` with esbuild.
- `scripts/build-monitoring-config.mjs` — generates runtime configuration from environment variables.
- `vendor/herdharbor-monitoring-v1.6.1.min.js` — generated reusable browser bundle.

The public API is exposed as `window.HerdHarborMonitoring` and provides the reusable service model requested for v1.6.1, including initialization, exception/message capture, explicit breadcrumbs, module context, anonymous user correlation, and controlled safe context.

Monitoring is optional and fail-open. The application boots even when the DSN is absent, Sentry is unavailable, initialization fails, the monitoring bundle cannot load, or event transport fails.

The Sentry Loader Script is not used. `Sentry.init()` is not placed in `index.html`.

Required products/settings for Phase 1:

- Logs: OFF

The runtime initialization additionally forces:

- `sendDefaultPii: false`
- `enableLogs: false`

- Replay/BrowserTracing integrations removed

## 3. Privacy boundary

Privacy filtering happens before an event is allowed to leave HerdHarbor and is applied in two layers: the core sanitizer and a final privacy adapter around the Sentry SDK.

The system intentionally does not transmit:

- passwords or passcodes
- bearer/access/refresh/session tokens
- Authorization headers or cookies
- API credentials or secrets
- customer names, emails, phone numbers, or addresses
- farm names
- medical/treatment contents
- financial/payment contents
- animal or farm notes
- pedigree contents
- free-text form contents
- uploaded documents or photos
- backup contents
- spreadsheet contents
- raw application state
- localStorage or IndexedDB contents
- request bodies
- sensitive response bodies
- Cloud Sync payloads

### beforeSend

`beforeSend` rebuilds the outbound event from a narrow allowlist. It does not merely delete a few known fields from an otherwise raw event.

Allowed diagnostic data is limited to information such as:

- event/reference ID
- safe error category
- environment/release/build/platform
- module
- operation/result
- controlled counts/status values
- safe stack-frame file/function/line/column metadata
- sanitized request method and URL without query string or fragment
- anonymous correlation ID

Exception messages are replaced with controlled generic text by error category. Raw exception messages are not sent.

### beforeBreadcrumb

Only explicit `herdharbor.action` breadcrumbs survive. Default click/form/fetch breadcrumbs are discarded.

Examples of acceptable breadcrumbs:

- `animals → edit → save`
- `breeding → pair_analysis → generate_prediction`
- `shows → add_result → save`
- `sync → upload_changes`

Record names, animal names, customer names, notes, field contents, email addresses, tokens, and payloads are not permitted in breadcrumbs.

## 5. Error coverage

Phase 1 coverage includes:

- uncaught JavaScript exceptions
- unhandled promise rejections
- application startup failures
- PWA/service-worker registration and update-check failures
- important Cloud Sync failures
- authentication failure signals
- localStorage write/remove failures
- IndexedDB open/transaction failures
- serialization/runtime exception categorization
- backup download failures
- spreadsheet import/export/report wrapper failures
- controlled major-module context
- rabbit genetics action context

HerdHarbor uses IndexedDB for bounded local recovery snapshots. The v1.6.1 adapter monitors only failure events from IndexedDB open/transaction operations. It never records the database name, object-store name, key, request arguments, or stored values.

Printed pedigree/PDF-style output is primarily browser-generated print/document output rather than a dedicated native PDF service. Failures that escape those flows are covered by the controlled global exception/rejection handlers. No pedigree/document contents are attached to monitoring events.

## 6. Cloud Sync taxonomy

Use these categories for Cloud Sync failures:

- `network_unavailable`
- `authentication_failure`
- `upload_failure`
- `download_failure`
- `conflict_failure`
- `serialization_failure`
- `invalid_response`
- `unexpected_sync_exception`

Only category, operation, result, online state, and other controlled metadata may be reported. Cloud rows, local records, merge payloads, account email, tokens, request/response bodies, and farm state are prohibited.

The existing v1.5.0 Cloud Sync implementation is intentionally not rewritten around Sentry. Monitoring observes its public status/session interfaces and failure boundaries so the production data model and synchronization behavior remain unchanged.

## 7. Anonymous user correlation

Never send email, full name, username, farm name, phone, or address.

When an internal account ID is available, the monitoring layer derives a one-way anonymous identifier before calling Sentry. The raw internal ID is not sent. If anonymous correlation cannot be created safely, events remain unassociated with a user.

## 8. User-facing reference IDs

Captured failures can return reference IDs such as:

`HH-7F2A91C4`

These IDs are safe to show to a user or request in a support report. They are also attached to the sanitized Sentry event as controlled diagnostic metadata.

Do not expose raw exception text, stack traces, database messages, API payloads, tokens, or server internals in the normal HerdHarbor UI.

## 9. Configuration variables

Primary variable:

`HERDHARBOR_SENTRY_DSN`

Additional build variables:

- `HERDHARBOR_MONITORING_ENVIRONMENT` — `development`, `test`, or `production`
- `HERDHARBOR_BUILD_ID` — build/commit identifier
- `HERDHARBOR_ENABLE_MONITORING_TEST` — enables the controlled test only outside production
- `HERDHARBOR_MONITORING_SOURCEMAP=1` — optionally generates an external JavaScript source map

The committed `herdharbor-monitoring-config.js` deliberately contains an empty DSN. Do not replace it with the real DSN in a commit.

## 10. Web and installed PWA

Web and installed PWA use the same Browser JavaScript project and DSN.

The service worker includes the generated monitoring bundle and runtime config in its static shell and uses network-first behavior for those files. The v1.5.0 update regression fix remains independent of Cloud Sync.

Platform tags distinguish ordinary browser and installed PWA execution when the browser provides the relevant signal.

## 11. Production GitHub Pages DSN setup

The live site is currently deployed from `main` through GitHub Pages. A branch-served static Pages site cannot safely generate a runtime config from an Actions secret. Alpha v1.6.1 therefore includes `.github/workflows/v1.6.1-pages-deploy.yml` as the approved secret-injection path.

The workflow is deliberately:

- `workflow_dispatch` only
- main-branch only
- not runnable as a production deployment from the v1.6.1 review branch
- dependent on the `HERDHARBOR_SENTRY_DSN` GitHub Actions secret

### Exact production setup

Perform these steps only after Alpha v1.6.1 is approved for deployment:

1. In the GitHub repository, open **Settings → Secrets and variables → Actions**.
2. Create a repository secret named exactly `HERDHARBOR_SENTRY_DSN`.
3. Paste the Browser JavaScript project DSN as the secret value.
4. Do not create a Sentry auth/API token for ordinary event delivery. The Browser SDK needs only the DSN.
5. After the approved v1.6.1 PR is merged, open **Settings → Pages**.
6. Change **Build and deployment → Source** from branch deployment to **GitHub Actions**.
7. Open **Actions → HerdHarbor Pages deploy with v1.6.1 monitoring**.
8. Choose **Run workflow** on `main`.
9. The workflow builds the monitoring bundle, generates `herdharbor-monitoring-config.js` from the secret, stages a Pages artifact, and deploys it without committing the generated DSN to Git.
10. Verify `https://app.herdharbor.com` loads normally before performing the controlled Sentry event.

The Browser DSN is necessarily visible to browsers in the delivered JavaScript configuration; that is normal for a client-side Sentry DSN. The requirement here is that the DSN is not committed to repository source. Sentry admin/API/auth tokens remain secret and must never be shipped to browsers.

## 12. Android Trusted Web Activity

The Android app is a Trusted Web Activity around the production web app. It should use the same Browser JavaScript Sentry project and DSN delivered by `app.herdharbor.com`.

No native Android Sentry SDK is added in Phase 1 because the current Android shell contains minimal native application logic and the meaningful HerdHarbor runtime executes as web JavaScript. Review CI builds an unsigned Android release bundle only; it does not publish to Google Play.

Reconsider a native Android crash SDK only if HerdHarbor later adds significant Kotlin/Java application logic or Android-specific crash evidence shows the TWA shell itself needs dedicated instrumentation.

## 13. iOS Capacitor JavaScript

The current submitted iOS v1.5.0 Build 9 is not modified by this work.

The Capacitor app stages local web assets into its `web` directory. For Alpha v1.6.1, the JavaScript running in the Capacitor WebView should use the same Browser JavaScript Sentry project/DSN as web/PWA/TWA and will be tagged `ios-capacitor` when Capacitor reports the native platform.

Before producing a future approved v1.6.1 iOS build, the separate Capacitor/Codemagic branch must be reconciled with the v1.6.1 JavaScript build rather than overwriting its Capacitor `package.json` dependencies.

The iOS staging script must include `herdharbor-monitoring-config.js`; its existing recursive `vendor/` staging then carries the generated Browser bundle.

### Exact future Codemagic variable path

For the first approved v1.6.1 iOS build:

1. Add `HERDHARBOR_SENTRY_DSN` as a **secure** Codemagic environment variable or secure environment-group variable.
2. Do not place the value in `codemagic.yaml`.
3. Before `npm run sync:ios`, run the v1.6.1 monitoring bundle build.
4. Generate config with `HERDHARBOR_MONITORING_ENVIRONMENT=production`.
5. Set `HERDHARBOR_BUILD_ID` to the iOS/Codemagic build number or a stable build identifier.
6. Ensure `herdharbor-monitoring-config.js` is copied into the staged `web` directory.
7. Verify the monitoring test in a non-production/TestFlight validation configuration before enabling production-only delivery.

Do not apply these changes to the already-submitted v1.5.0 Build 9.

## 14. Recommended native iOS crash strategy

Browser JavaScript monitoring cannot capture every Swift/Objective-C/native process crash. Native iOS crash reporting should therefore be a separate implementation step after the currently submitted build is no longer at risk.

Recommended architecture:

- add the Sentry Cocoa/iOS SDK to the Capacitor Xcode project through Swift Package Manager
- initialize it in native application startup before substantial native work begins
- use a dedicated native iOS Sentry project/DSN for clear separation of native crash groups from Browser/WebView JavaScript issues
- keep PII collection disabled
- leave Replay, tracing/performance, profiling, logs, and metrics disabled unless separately approved
- use the same logical release version `HerdHarbor@1.6.1` and associate the iOS build number as the distribution/build identifier
- upload dSYMs from Codemagic using a Sentry CI authentication token stored only as a secure Codemagic secret
- never place a Sentry auth token in the app bundle or repository

The current iOS project has no native Sentry dependency and its `AppDelegate` contains no Sentry initialization, so native crash capture is not silently assumed to exist.

## 16. Source maps

The v1.6.1 bundle is minified, so source maps are worthwhile for actionable JavaScript stack traces. They are intentionally not uploaded automatically yet because source-map upload requires Sentry CI credentials and the controlled event path must be validated first.

Current build support:

`HERDHARBOR_MONITORING_SOURCEMAP=1 npm run build:monitoring`

This produces an external map without embedding original source contents into the map.

Recommended implementation after the first controlled Sentry event succeeds:

- Web/PWA/Android TWA: generate/upload the map in GitHub Actions.
- iOS Capacitor JavaScript: generate/upload from Codemagic for the exact staged bundle/build.
- Native iOS: upload dSYMs from Codemagic.
- Use release `HerdHarbor@1.6.1` and a build/dist matching `HERDHARBOR_BUILD_ID`.
- Store any Sentry CI auth token only in GitHub Actions/Codemagic secrets.
- Do not commit auth tokens or expose them in the browser configuration.

Sentry release/source-map APIs require authenticated CI credentials; ordinary Browser event delivery does not.

## 17. Controlled Sentry test

The controlled crash API is available only when:

- environment is not `production`, and
- `HERDHARBOR_ENABLE_MONITORING_TEST` is true.

It is unavailable to ordinary production users.

### Local controlled test procedure

From a clean checkout of `agent/v1.6.1-crash-monitoring`:

1. Install dependencies with `npm ci`.
2. Set `HERDHARBOR_SENTRY_DSN` in the shell environment; do not edit the committed config file manually.
3. Set `HERDHARBOR_MONITORING_ENVIRONMENT=test`.
4. Set `HERDHARBOR_BUILD_ID=controlled-sentry-test-1`.
5. Set `HERDHARBOR_ENABLE_MONITORING_TEST=true`.
6. Run `npm run build:monitoring`.
7. Run `npm run build:monitoring-config`.
8. Serve the repository through a local HTTP server rather than opening `index.html` as a `file://` URL.
9. Open HerdHarbor in the browser.
10. In the browser console run `HerdHarborMonitoring.testCrash()`.
11. Record the returned `HH-XXXXXXXX` reference ID.
12. In Sentry, verify an event actually appears before marking real delivery PASS.
13. Verify the event shows environment `test`, release `HerdHarbor@1.6.1`, the configured build, platform, module, safe breadcrumb/context, and reference ID.
14. If an anonymous user was set through the normal app session, verify only the `anon-*` identifier is present.
15. Inspect the final event for privacy: no email, name, phone, address, notes, request body, auth token, customer/farm/animal contents, spreadsheet contents, or backup contents may appear.
16. Restore the committed blank config before committing anything: `git checkout -- herdharbor-monitoring-config.js`.

Do not call real Sentry delivery PASS merely because unit tests pass. PASS requires the event to be visible in the configured Sentry project.

## 18. Automated verification

The branch review workflow:

- installs pinned dependencies with `npm ci`
- builds the Browser monitoring asset
- verifies the generated asset exists
- runs every `tests/*.test.cjs` in `TZ=UTC`
- runs every `tests/*.test.cjs` in `TZ=America/New_York`
- verifies environment-driven config generation using a fake DSN
- checks the source tree is not mutated unexpectedly
- builds an unsigned Android release bundle as a TWA compatibility check
- uploads review artifacts only

Privacy tests inject fake passwords, access/refresh/session tokens, Authorization headers, customer contact data, payment/financial data, health/animal/farm notes, free text, request bodies, backup/spreadsheet contents, sensitive URL parameters, and unsafe breadcrumbs, then prove those values do not survive final outbound sanitization.

## 19. Troubleshooting

### No events appear

Check:

- `HERDHARBOR_SENTRY_DSN` was actually present when config was generated
- the generated runtime config is the one served to the browser
- the environment is `test` or `development` for the controlled test
- `HERDHARBOR_ENABLE_MONITORING_TEST=true`
- the browser can reach Sentry
- an extension/content blocker is not blocking event transport
- the Sentry project/environment filters include the event

If the DSN is blank, monitoring intentionally disables itself and HerdHarbor continues normally.

### App starts but monitoring bundle fails

This is expected fail-open behavior. HerdHarbor must remain usable. Check the static asset path and service-worker cache without changing farm records.

### Too many duplicate events

The service has duplicate suppression and hourly volume limits. Expected offline behavior uses a longer suppression window. Do not add general click/navigation logging to compensate for sparse events.

## 20. Disabling monitoring

For a test/deployment where monitoring must be disabled, serve a runtime config with an empty DSN. No application feature should depend on Sentry being available.

For production rollback, remove/withhold the DSN through the deployment environment and regenerate the config. Do not remove application data or alter account access to disable monitoring.

## 21. Verifying privacy before every release

Before approving a monitoring release:

1. Run the complete regression suite in UTC and America/New_York.
2. Run the privacy tests.
3. Inspect the generated bundle and runtime config.
4. Confirm no real DSN or Sentry auth token is committed.
5. Enable **Prevent Storing of IP Addresses** (`scrubIPAddresses=true`) in the Sentry project or organization privacy settings.
6. Run the controlled Sentry event in a non-production environment.
7. Inspect the actual event in Sentry for prohibited data, including IP-derived user or geo context.
8. Verify the `HH-XXXXXXXX` reference ID matches.
9. Verify Error Monitoring works with Replay/Logs/Tracing/Metrics still disabled.
