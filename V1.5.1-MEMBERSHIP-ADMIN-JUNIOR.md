# HerdHarbor Alpha v1.5.1 access architecture

## Central policy

`window.HerdHarborMembership` is the only client policy layer for membership access and active-animal limits. Screens must call it rather than interpreting role, tier, or subscription state independently.

| Concern | Values | Purpose |
| --- | --- | --- |
| Account role | `owner`, `admin`, `user` | Administrative permission |
| Membership tier | `junior`, `founder`, `member`, `business` | Product entitlement and limits |
| Membership source | `default`, `subscription`, `founder`, `manual_override` | Why the tier is active |
| Account status | `active`, `disabled` | Account availability |

The first-use client fallback is User + Member + Default + Active. After an authenticated access record has loaded successfully, HerdHarbor stores a minimal per-UUID entitlement snapshot containing only role, tier, source, status, override expiration, and verification time. An offline restart reuses that account's last verified tier, so a known Junior remains limited to five active animals. A different account never reads that snapshot because the cache key and embedded `user_id` must both match its authenticated Supabase UUID.

## Supabase contract

The client reuses the current authenticated Supabase instance and the installed foundation:

- `public.account_access`
- `public.admin_audit_log`
- `public.herdharbor_account_role()`
- `public.admin_set_account_role(...)`
- `public.admin_set_membership(...)`
- `public.admin_return_to_automatic_membership(...)`
- `public.admin_member_directory()` after running `supabase/v1.5.1-admin-member-directory.sql`

The database remains authoritative for Owner/Admin authorization. RLS permits a user to read their own access record. Normal authenticated users cannot update `account_access`. Administrative changes use the installed security-definer RPCs with their exact production parameter names, validate the acting account, protect the single Owner, and append immutable audit history.

The protected directory RPC joins the allowlisted administration fields in `account_access` to Auth email, display-name metadata, account creation, and last sign-in inside Supabase. Its `SECURITY DEFINER` body checks `auth.uid()` against an active Owner/Admin row before returning anything. Browser code receives no direct `auth.users` access and no service-role credential.

The permanent Owner is identified by the authenticated UUID in `account_access`. No email address is hard-coded in the app.

## Admin permissions

Authorized Owner/Admin accounts can search the protected directory by name, email, or UUID; filter by tier, role, or status; inspect administrative history; change User/Admin roles; set a membership override; and return an account to automatic membership.

The client never offers Owner as an assignable role. Supabase remains responsible for preventing Owner demotion, a second Owner, unauthorized self-promotion, audit bypass, and changes from disabled or ordinary accounts.

The current farm-state model intentionally keeps each user's livestock records private. Because there is no server-maintained cross-account usage summary, Admin displays cross-account active-animal usage as “Not exposed.” It never opens another member's farm JSON to calculate a count. Email, display name, and last-login metadata come only from the protected allowlisted directory RPC.

Installed mutation signatures:

```text
admin_set_account_role(target_user, new_role, change_reason)
admin_set_membership(target_user, new_tier, change_reason, expires_at)
admin_return_to_automatic_membership(target_user, change_reason)
```

The browser makes one call with those exact parameters. It does not probe or retry guessed signatures.

## Membership resolution

Resolution order is:

1. Active manual override.
2. Founder/grandfathered access.
3. Active billing entitlement when billing is enabled.
4. Stored/default membership.

An expired manual override resolves to automatic Member access while billing is disabled. The historical audit entry remains intact. The secure backend should perform the same expiration resolution before billing activation so all devices agree even before app startup.

## Junior

Junior has the current HerdHarbor core feature set and five active-animal slots. Sold, Deceased, Archived, and Ancestor Only records do not count.

The limit is checked through one transition rule:

```text
allowed = afterActive <= 5 OR afterActive <= beforeActive
```

This permits an already over-limit downgraded herd to remain visible and editable and permits the user to reduce its active count. It blocks any operation that increases the active count while it remains above the limit. The app applies the rule to manual creation, reactivation, litter offspring, transfer import, spreadsheet import, and demo data. Backup restore and Cloud Sync never discard records; after restoration or merge, the same transition rule prevents further growth until usage is compliant.

Upgrading Junior to Member changes only the access record. It does not copy or migrate farm data.

The offline entitlement snapshot is separate from farm-state and Cloud Sync storage. It contains no email, name, animal, medical, customer, financial, token, or session data. A successful reconnect refresh replaces it with the current authoritative `account_access` result. Expired manual overrides are re-evaluated against the current time even while offline.

## Billing-ready boundary

`window.HerdHarborBilling` centralizes future provider state and recognizes active, trialing, resubscribed, founder, free-Junior, payment-failed, past-due, canceled, and expired outcomes. The adapter maps provider entitlements to the centralized membership policy.

For this review build, `billingEnabled` is `false`. No store SDK is initialized, no provider endpoint is called, no payment is requested, and Member remains the automatic default. Founder is recorded at $7.99/month grandfathered, Member at $14.99/month, Junior free, and Business reserved. Store product configuration and live entitlement synchronization require separate credentials, store review, and explicit activation approval.

- Build the monitoring bundle from the pinned lockfile.
- Build the unsigned Android review AAB.
- Verify the Sentry configuration from environment secrets and send a controlled test event.
- Validate Owner, Admin, and User accounts against live RLS/RPCs.
- Run `supabase/v1.5.1-admin-member-directory.sql`, then verify Owner/Admin results and an ordinary User denial.
- Validate a newly registered account resolves to User + Member + Default + Active.
- Validate Junior at 0, 1, 4, and 5 active animals, sixth-animal rejection, slot release, import, transfer, backup restore, Cloud Sync, and multi-device behavior.
- Do not merge, deploy, enable billing, or publish store builds until acceptance is explicitly approved.
