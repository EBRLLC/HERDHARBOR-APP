# S20 — Login upgrade and normalized-only signup (candidate)

## User-facing contract
Existing breeders: login -> hydrate authoritative legacy data -> finish pending cloud sync -> verify normalized dual-write reconciliation -> offer an upgrade only if owner-controlled server flags confirm off-device backup and shutdown of old clients -> download a local safety copy and confirm other devices closed -> S18 performs three independent validations and promotes to normalized authority -> legacy rows retained as recovery only. A pending PWA update takes precedence over switching authority.

New signups (after a separately authorized database trigger deployment): auth.users AFTER INSERT trigger creates the **only** initial cloud dataset in `herdharbor_sync_records`: an empty but fully formed canonical normalized checkpoint. It creates a normalized authority manifest and enrollment row, and it **does not** insert `herdharbor_user_data`. The existing S18 hydrated normalized baseline is responsible for first-login setup. Subsequent local edits flow to the normalized record-outbox writer.

## Included code
- `scripts/sql/s20-new-normalized-signups.sql` — staged database trigger, not applied.
- `s20-login-normalized-upgrade.js` — safe upgrade prompt, with independently written server-approval markers. It never flips approval bits.
- `herdharbor-cloud.js` — emits authenticated hydration completion only after account boundary and unlocked app checks.
- `index.html`, `service-worker.js` — coordinated S20 script inclusion, cache identity and version references.
- `tests/v2.0.1-s20-normalized-signup.test.cjs` — structural, checksum and approval-gate tests.

## Hard safeguards
1. Do NOT deploy the signup trigger until compatible 2.0.1 site and PWA are verified and there is a controlled plan for older 2.0.0 client windows. Existing 2.0.0 code cannot save into normalized authority. An already-open older page cannot be remotely rewritten. Coordinate the switch with an owner-approved maintenance window or a verified bridge and enforce compatible clients for new signups.
2. The client only offers a conversion if the Supabase manifest has `s20_client_cutover_approved`, `s20_offdevice_backup_verified`, and `s20_legacy_clients_closed` all true. These must come from independent operational acceptance, **not from a client request**. A checked box alone never proves all devices are closed.
3. Existing S18 `cutoverToNormalizedPrimary` does final, generation-fenced repeated reconciliation. Failed verification leaves legacy authoritative and local edits protected.
4. No legacy row/schema is deleted in S20. After normalized authority activates, the existing production trigger blocks outdated full-state writes. Recovery data remains retained.
5. Existing 2.0.0 PWA's 8-second forced reload remains a release blocker and is **not** fixed merely by changing the newer worker.
6. A safety backup download is an *additional* convenience. The separate server-side verified backup is mandatory; the browser cannot cryptographically prove the user retained the downloaded file.
7. New normalized users have an initial empty `{}` snapshot. Run actual browser signup, onboarding save, logout/login, second-device read, offline mutation outbox, CAS conflict and subscription tier tests in staging before activation. A green static SQL test does **not** prove runtime onboarding works.

## Required launch sequence
1. Resolve S17 old-PWA upgrade, GitHub Pages source settings and production release gates. Validate S20 scripted app assets + full exact-head CI.
2. Rehearse `scripts/sql/s20-new-normalized-signups.sql` in isolated staging. Use real staging signup and cross-device sessions; never generate synthetic production users.
3. Rehearse S19 source-preserving migration for all five customer backup copies, with missing-manifest and dual-write paths, 3-pass reconciliation, record identity/tombstones, rollback and offline client recovery.
4. With owner approval, deploy the compatible web/PWA build, then activate signup trigger in a controlled window with a strategy preventing old signup client writes. Confirm new users go straight into normalized saving.
5. Migrate existing accounts one by one only when server acceptance flags and off-device backups have been verified. Preserve legacy rows and restoration process.
6. Monitor normalized record CAS failures, outbox pending, account boundary errors and PWA update deferrals. Do not retire legacy recovery until separate retention approval.
