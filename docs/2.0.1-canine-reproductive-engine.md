# HerdHarbor 2.0.1 — Canine Reproductive Engine (PR B)

## PR B — Reproductive planning milestone

PR B adds an opt-in canine workspace reachable from a female Dog's existing animal detail. It records multiple historical heat cycles, breeder observations, laboratory progesterone observations, veterinary appointments and clinical interpretations, veterinarian-confirmed ovulation, account-scoped external stud references, plans, multiple mating events, pregnancy status, and transparent expected-whelping dates or ranges. It creates stable tasks for planned breeding, assessment, expected whelping, and custom cycle reminders.

The UI does not calculate a fertile period, infer a reproductive stage or ovulation date from elapsed time, interpret a single laboratory value, confirm pregnancy after mating, or infer puppy parentage from a plan sire. Different Dog breeds are allowed. An external sire is a reference object and is not represented as a privately owned animal.

## Optional state model

- `canineReproductiveCycles[]`: independent records keyed by stable `id` and `femaleId`; date-only heat start, optional observed stage, status, observations, lab results, vet appointments, clinical interpretations, explicit veterinarian-confirmed ovulation, event history, custom reminders, and linked `breedingAttemptIds`.
- `canineExternalStuds[]`: account-scoped records keyed by stable `id`, tagged `ownerScope: "external_reference"`, with registered/display name, breed, registry/number, titles, and optional later `linkedAnimalId`. Duplicate registry/number or registered-name/breed keys are rejected within that account.
- `canineBreedingPlans[]`: dam ID, tagged sire reference, optional cycle ID, planned dates/method, breeder-entered registration and health-testing notes, status, nested `events[]`, and a pregnancy record. Event sire references can explicitly remain `unknown` or name different potential sires.
- `tasks[]`: stable plan reminder IDs (`task_canine_<planId>_<kind>`) and stable cycle reminder IDs. Cancellation completes only records whose source type and source record ID match the plan or cycle.

All fields are additive to the existing canonical account state. No Supabase schema, normalized-primary migration, or production data is changed. Legacy records can omit all canine reproduction arrays.

## Save and synchronization semantics

Each workspace transaction clones canonical state, validates the target female, species, sex, sire reference, and submitted dates before committing, and calls the existing `HerdHarborApp.commitState(next, message)` boundary. That API reports a successful local state-store commit and restores the in-memory state if local persistence fails. It does not prove that the cloud has acknowledged or synchronized the change; the UI states that synchronization may still be pending.

The workspace also compares the open canine cycles, plans, external studs, and plan-owned tasks to the latest in-memory state before each transaction. A stale same-tab edit is rejected and the workspace refreshes to the latest state. This is not cross-device compare-and-swap: the existing 2.0.1 whole-state/cloud workflow does not expose a per-record server CAS guarantee for these new arrays. Cross-device conflict and reconnect acceptance remain PR D release blockers; no claim of synchronized end-to-end safety is made here.

## Dating rules

- Breeding-date estimates are a broad 58–72 day range from the first through last recorded completed mating date.
- Veterinarian-confirmed ovulation estimates are 62–64 days after the recorded date.
- Veterinarian-provided and manual ranges are persisted as supplied and are not automatically replaced by unrelated edits.
- Date-only calculations use UTC calendar arithmetic; the date entry default is formatted from the device's local calendar to avoid a midnight timezone shift.
- No automatic estimate is emitted without a relevant completed mating or veterinarian-provided ovulation/date evidence.

The veterinary references and their limits are recorded in [the audit report](2.0.1-canine-breeding-audit.md).

## Rollback and release blockers

PR B can be reverted without a schema downgrade because it adds only optional canonical state fields and static web assets. New fields are not guaranteed to survive an older whole-state client writing a snapshot; before production release, verify older-client read/write behavior and cross-device reconnect behavior, and provide a compatibility strategy if it can drop the new arrays. Do not remove records to roll back. Keep a verified account backup and perform save, reload, and old/new client checks before any merge decision.

PR C adds canine whelping and linked canonical litter records, retry-safe stable puppy IDs with partial-state reconciliation, reference-only external sire ancestors, later evidence-noted individual parentage, existing canine lineage validation, and dog-specific puppy weights, health entries, and identity fields in the shared Manage Litter workspace. It keeps canine whelping identity and birth dates out of generic litter edit/delete actions. See [the PR C implementation note](2.0.1-canine-whelping-implementation.md).

PR D still needs shared dashboard/notification acceptance across reload and offline reconnection, realistic browser/device acceptance, performance review, and a release rollback runbook. Cross-device compare-and-swap is not available in this release's whole-state save architecture, so the implemented retry safety does not guarantee conflict-free concurrent writes from independent clients. This milestone stack is not a production release recommendation.
