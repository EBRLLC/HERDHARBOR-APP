# HerdHarbor 2.0.1 Canine Breeding — Audit and Implementation Record

**Audit baseline:** `main` at `e1cbc39b67d02f528ff4528c6f2addda7130c7d6` (2026-10-26), after merged PR #511. The 2.0.2 normalized-cloud work remains isolated in PR #506. No production database or release settings were changed.

## Existing reusable components

- Canonical state holds `animals`, `breedings`, `litters`, `tasks`, `health`, and activity records. The extracted breeding runtime writes through this state and the existing canonical state store.
- `breeding-litter-runtime-v1.8.3.js` already owns breeding/birth forms, basic reminders, a single breeding-date schedule for supported species, deterministic birth/offspring IDs, and birth outcome validation.
- `breeding-next-action-core-v1.8.2.js` and the shared task runtime provide derived dashboard actions and task behavior.
- `breeding-litter-workspace-v1.8.2.js` already provides shared litter weights, health events, identity, loss, weaning, and disposition operations for canonical offspring records.
- `canine-identity-v2.0.1.js`, `canine-breeds-v2.0.1.js`, and `canine-lineage-v2.0.1.js` provide dog identity, breed/color/marking selection, and canine ancestry validation. `pedigree-engine-v2.0.0.js` builds pedigrees from canonical animal records.
- `herdharbor-app-runtime.js` supplies `saveState()`, which reports whether the canonical **local** state commit succeeded. This return value does not establish successful cloud synchronization; cloud sync can remain queued/dirty after the local commit.

## Confirmed defects

1. `renderLitters()` calls the singular `$()` selector for `[data-edit-litter]` and `[data-create-offspring]`, then calls `.forEach()`. `$()` is `querySelector`; these calls fail with no matching button and cannot cover multiple buttons. The collection helper is `$$()`/`querySelectorAll`.
2. Breeding and birth create/edit/delete, and bulk offspring generation, mutated canonical records, relationships, reminders, and activity before calling `saveState()`. The handlers then closed and rerendered even if the save returned `false`. A local durability failure could therefore leave uncommitted state in memory and report success.
3. Existing generic canine lineage expects parent IDs to resolve to canine animal records, which does not model a private external stud safely.
4. Existing `GESTATION_RULES` included a single `Dog: 63` rule based on breeding date. It was presented as a single due date and shared workflow statuses/tasks with other species. PR A removes that automatic canine calculation while preserving any breeder-entered date; rabbit and other established schedules remain in place. The foundational canine helper provides source-labeled windows instead.

## Missing canine functionality

- Historical heat cycles and dated observations, tests, veterinary interpretations, and cycle events.
- Multiple planned and completed breeding events per cycle, external stud references, and unresolved/multiple-sire parentage.
- Separate transparent breeding-date ranges, veterinarian-confirmed ovulation dating, veterinarian-supplied dates, and breeder-entered manual estimates.
- Canine pregnancy assessment/status workflow, canine reminder types, whelping outcome records, and individual puppy creation/reconciliation.
- Puppy development workspace support without changing rabbit behavior; canine-safe parent references, account scope, ancestry and registration preservation.
- End-to-end retry/concurrency handling across clients. Stable IDs already exist for offspring, but generation currently computes available slots from current local records and does not reconcile uncertain concurrent commits.

## Proposed additive data structures (no database migration)

All structures are optional fields nested within the existing canonical account state and are backward-compatible when absent:

- `animal.canine`: optional canine-only identity, lineage, registration, and coat metadata already introduced by 2.0.1; future fields must remain optional.
- `canineReproductiveCycles[]` (PR A/B): `{id, femaleId, observedHeatStartDate, observedStage, status, observations[], veterinaryAppointments[], progesteroneTests[], clinicalInterpretations[], customReminders[], ovulation, fertileEstimate, notes, eventHistory[], breedingAttemptIds[]}`. Raw progesterone observations remain uninterpreted; an entered clinical interpretation is stored separately.
- `canineExternalStuds[]` (PR A/B): `{id, accountId, displayName, registeredName, breed, registry, registrationNumber, titles, ownerScope:'external_reference', linkedAnimalId?, notes, createdAt, updatedAt}`. References are account-local; no lookup of another member’s private records.
- `canineBreedingPlans[]` (PR B): `{id, damId, sireRef, cycleId?, plannedDates[], plannedMethod, healthTesting, registrationDetails, status, notes, events[], pregnancy}` where `sireRef` is a tagged union for a same-account dog, account-scoped external stud, or unknown reference.
- Each plan’s `events[]` entry is `{id, planId, cycleId, date, time?, method, sireRef, outcome, veterinaryInvolvement?, notes}`. Multiple sires and unknown paternity are explicit; no puppy parentage is inferred from the plan sire.
- Each plan’s `pregnancy` stores explicit status, veterinary evidence fields, and a dating estimate with source method (`breeding_range`, `vet_confirmed_ovulation`, `vet_expected`, `manual`), source date, date/range, `calculated`, `userAdjusted`, and calculation timestamp.
- Canine task IDs use stable plan/type keys and cycle/reminder IDs. Cancellation closes only tasks owned by that source record.
- `canineWhelpings[]`: `{id, litterId, damId, sireRef?, cycleId?, planId?, date, time?, method, bornAlive, stillborn, neonatalLosses, vetInvolvement, notes}`; individual puppies remain canonical `animals` with stable IDs and `sourceBirthId`/litter relationship.
- Canine task IDs use stable record/type keys and canine-specific source types; cancellation closes only tasks owned by that source record.

Veterinary timing basis for the foundational date helper: Cornell describes the broad breeding-date uncertainty (about 63 ± 7 days from the first mating) and about 63 ± 1–2 days from known ovulation; Merck lists 58–72 days from mating when cycle timing is unknown and 62–64 days from ovulation. The core returns a **range**, labels it as an estimate, records its source method, and never derives cycle stage or ovulation from elapsed days or a single progesterone result. See [Cornell Riney Canine Health Center: Normal Whelping Process](https://www.vet.cornell.edu/departments-centers-and-institutes/riney-canine-health-center/canine-health-topics/normal-whelping-process) and [Merck Veterinary Manual: Approximate Gestation Periods](https://www.merckvetmanual.com/multimedia/table/approximate-gestation-periods).

PR A/B use tolerant readers for old records with absent fields and additive optional arrays; they preserve existing IDs and add no schema migration. External studs are reference-only and remain outside the canonical animal collection. Whelping records, puppy generation, lineage integration for external references, and dog Manage Litter extensions are deferred to PR C.

## Backward-compatibility and release risks

- `breedings` and `litters` are currently used by rabbit and other species; dog behavior must be explicitly species-gated, with legacy rabbit defaults and terminology unchanged.
- New optional account-state properties survive JSON canonical-state persistence, but a normalize/allowlist layer could drop unknown fields; that boundary must be checked before adding them.
- The existing `sireId`/`damId` lineage contract cannot simply receive an arbitrary external ID. A tagged parent reference or an explicitly compatible reference-only animal is needed before generating external-sire puppy pedigrees.
- Canine calendar math must be date-only and timezone independent. UI-local midnight conversions should not alter the stored date.
- PWA script cache identities and loader lists require coordinated revision bumps whenever a new asset is added or edited.
- A local save success is not cloud confirmation. Release claims must distinguish local durability, pending cloud/outbox state, and server acknowledgement.
- New nested records are not covered by rollback of an old deployed client if a client rewrites a whole older state snapshot. Preserve fields during compatibility review and defer merge until old-client behavior is understood.

## Rollback and recovery

- Keep changes additive and optional; do not remove or rewrite existing `breedings`, `litters`, animals, tasks, or cloud sync paths.
- Roll back application code to the recorded parent commit. Since this plan avoids a schema migration, code rollback does not require a database downgrade.
- Before any release, export and verify an account backup and exercise save/reopen using both current and previous PWA clients. If newly added fields are not preserved by older clients, block release or provide a separately approved compatibility bridge.
- On a failed local commit, restore the pre-action canonical in-memory snapshot, leave the modal open, and do not emit success activity/reminders. Offline local durability remains distinct from cloud sync.
- Do not merge/deploy without explicit owner authorization; PR #506 stays untouched.

## PR boundaries

- **PR A — stabilization/foundation:** selector bug and failed-local-save rollback, tests, audit report, additive canine reproductive schema/validators and foundational compatibility tests. No cloud migration.
- **PR B — reproductive engine:** cycles, observations/tests, plans/events, external studs, evidence-aware dating/statuses, canine reminders, UI, tests.
- **PR C — whelping/puppy records:** litter links, idempotent generation/reconciliation, lineage/registration, dog Manage Litter view, tests.
- **PR D — release hardening:** dashboard integration, browser and offline/account-switch tests, full suite, security/PWA/print review, rollback and acceptance checklist.

Implementation starts with PR A. PR boundaries may be adjusted only when shared-state contracts require it; any adjustment must be recorded here before dependent implementation.
