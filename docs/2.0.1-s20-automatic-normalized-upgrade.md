# HerdHarbor 2.0.1 — S20 Automatic Normalized Upgrade / Normalized-Only Signup

Status: **CODE CANDIDATE. Do not merge or deploy without staged acceptance.**

## Existing breeder accounts
- On authenticated hydration the S20 coordinator checks the **actual** rollout manifest and whether the device is clean, online, free of conflicts and record-outbox entries. The app never switches the cloud writer just because a rollout feature is enabled.
- Previously unbootstrapped allowlisted accounts use the existing S18 safe `legacy -> shadow -> dual_write` bootstrap. The normalized verifier compares the current authoritative legacy snapshot, normalizer checksums, record content/count and manifest checkpoint. This validation runs before a migration prompt.
- A visible opt-in prompt requires the breeder to explicitly confirm that **other old devices and windows have saved and closed**. There is no way for the cloud alone to prove the absence of an unsubmitted draft on an offline iPhone.
- On acceptance, S20 revalidates cloud vs normalized records. A waiting service worker update is offered through the existing guarded PWA Update Now UI, not activated silently. A tab-scoped account-specific continuation marker allows new code to finish the transition after reload. Without a waiting update, the current updated client can proceed directly.
- Immediately before authoritative cutover, S20 verifies the legacy cloud save, archives the cloud snapshot and any different local snapshot, and delegates to the original S18 guarded `cutoverToNormalizedPrimary()` (three required reconciliations, CAS manifest cutover, normalized read verification and safe rollback handling). A source change or pending outbox blocks promotion.
- Existing normal cloud save code routes to per-record CAS/outbox after a verified normalized stage. Old legacy writers are blocked by the pre-existing database trigger. The legacy table and its backups are retained **for read-only recovery**, not as an active fallback.

## New accounts
- `supabase/v2.0.1-s20-normalized-only-signup.sql` installs an AFTER INSERT trigger on `auth.users`. Only accounts created **after applying the migration** are affected; it never backfills or changes existing users.
- In the same signup transaction it seeds one canonical `legacy-state/snapshot-manifest` for the empty `{}` state and the normalized authority manifest. It performs the existing strictly adjacent guarded manifest transitions *inside the uncommitted transaction*, with a temporary internal cohort row that is removed before commit. **It never creates a `herdharbor_user_data` row.**
- The database trigger fails the entire signup if any stage or record write fails, preventing a new account from being created with an uninitialized cloud writer.
- Already normalized accounts are eligible for runtime authority recovery without needing a permanent internal test cohort. The S20 client waits for the authoritative normalized hydration decision before fetching any legacy record (including the former eager prefetch).
- Brand-new normalized accounts must save their first animal/task normally through the existing CAS/outbox worker. The empty checkpoint is checked using the canonical v1.8.3 normalizer checksum.

## Compatibility / release safety gates
1. **SQL-before-client deployment is not safe while signup remains publicly accessible on older 2.0.0 clients.** Coordinate a maintenance window or other verified registration/update gate so a user cannot create a normalized-only account in a legacy-only client. Do not create live accounts during the transition.
2. S17's already-loaded 2.0.0 eight-second forced reload cannot be retroactively fixed. Owners must verify saved and closed old clients before pressing Update Now, or authorize a separately rehearsed bridge release.
3. Do **not** activate production normalized authority until a current off-device recovery export and a nonproduction SQL execution + restoration rehearsal are independently verified; client-side snapshots alone do not substitute for that backup.
4. Acceptance must cover real iPhone/Android/desktop updates, A→B→A identity races, two-device CAS conflicts, offline/dirty draft preservation, duplicate-ID animal/litter records and normalized saves after a fresh sign-in.
5. SQL and client code deploy in a coordinated release; no untested standalone trigger update, direct production migration, table deletion or forced old-device overwrite.
