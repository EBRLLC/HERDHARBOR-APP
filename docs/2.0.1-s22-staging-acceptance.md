- Record the deployed schema migration hash, tested Git SHA, isolated project reference, database checksums, device/browser versions, UTC timestamps, artifacts and tester initials. Redact emails, secrets, tokens and private animal records.
- An actual write test and a restored backup are required. Green repository CI **alone cannot pass this gate**.

## Existing Auth-only account provisioning: separate operator gate

The five pre-existing Auth-only users are **not** equivalent to newly created
normalized-only accounts. Their missing legacy cloud row and missing normalized
manifest establish only server absence, **not** a verified empty account.
S22-23 is a mandatory fail-closed regression, not a provisioning authorization.

For each such account, record an account-specific approval and evidence bundle:

1. Identify every installed app/PWA/browser profile and capture its release
   revision, current user identity, local-state/IndexedDB recovery status,
   offline queue/dirty marker, and any existing offline edit. Do not sign out
   or clear caches until readable local exports and attachment copies exist.
2. Preserve and independently open an off-device export from every
   data-bearing device. Confirm species, animal/litter counts, lineage, notes,
   tombstones, photographs/attachments and stable IDs, including cross-species
   duplicate IDs. Keep all original files before any import attempt.
3. Reconcile competing device copies explicitly. If even one device cannot be
   checked or an export cannot be decoded, classify the account **HOLD**.
4. In an isolated Supabase instance, test one of two paths:
   * **Nonempty local state:** normalize the reviewed export, check record
     digests, preserve tombstones and attachments, and restore/import into a
     verified manifest under the exact user; test refresh/relogin on two devices.
   * **Verified empty on all devices:** use a separately reviewed,
     operator-only transactional initializer (not the Auth INSERT trigger),
     proving absence of remote rows and local data before seeding the canonical
     empty normalized checkpoint.
5. Require device-to-cloud parity, an independent restore proof, fresh-login
   CAS/outbox save and explicit owner approval before any production account
   action. Never auto-provision `{}` solely because the remote row is absent.

**No existing-account initializer or customer-data repair is approved by this
document.** A tested script and restore evidence are prerequisites. No
current production Auth-only account has been provisioned by S22.

## Normalized-only authority downgrade protection

A pre-existing authenticated RPC supports stage rollback for older accounts.
That behavior is unsafe for a normalized-only signup, which has no legacy
source. The pending S20 SQL therefore installs
`hh_s20_guard_normalized_only_signup` to reject downgrades from normalized
or removal of the `s20_signup_normalized_only` marker. Its anonymous
signup-readiness signal must fail closed if the guard is missing or disabled.
S22-24 requires real staged rollback attempts, negative permission checks,
and proof that normal normalized CAS/outbox writes continue afterward.
Recovery for these accounts must retain normalized authority and use verified
normalized backups; no implicit legacy rollback is available.

## Promotion order — only after every gate passes

1. Independently preserve off-host production recovery sources and **restore** them in isolation.
2. Complete all staging signup, account, CAS/RLS, migration, cross-device and recovery tests above.
3. Confirm all production account-creation paths support the S22 compatibility guard; older clients may sign in but must not register.
4. Coordinate and verify that all five cohort users' older devices are synced and closed; no remote observer can prove offline drafts were submitted.
5. Owner signs off on a one-account canary, rollback plan, monitoring and release window. Do **not** silently bulk-promote all five.
6. Only with explicit production authorization apply the reviewed SQL and release candidate, migrate one account, validate cloud/device parity, then proceed gradually.
7. Keep legacy rows **read-only for recovery** for a defined retention period. No legacy table deletion during S22.
