# HerdHarbor 2.0.1 — S22 staging acceptance and production hold

**Status:** RELEASE HOLD. This file is a test protocol, not evidence of execution.
**Scope:** PR #497, normalized-only signup, first-save CAS/outbox, existing-account migration.

## Non-negotiable environment protections

- Use a separate, **approved** Supabase test instance/branch with its own Auth URL/key and synthetic user data. Preview branching may incur charges. Never conduct signup, migration, deletion, or recovery writes against production to satisfy this checklist.
- Do not populate staging with real breeding/member records unless explicitly authorized and independently protected. Synthetic fixtures should contain rabbit/dog mixed-species, duplicate IDs in distinct namespaces, attachments, tombstones, and multi-device edits.
- Record the deployed schema migration hash, tested Git SHA, isolated project reference, database checksums, device/browser versions, UTC timestamps, artifacts and tester initials. Redact emails, secrets, tokens and private animal records.
- An actual write test and a restored backup are required. Green repository CI **alone cannot pass this gate**.

## Promotion order — only after every gate passes

1. Independently preserve off-host production recovery sources and **restore** them in isolation.
2. Complete all staging signup, account, CAS/RLS, migration, cross-device and recovery tests above.
3. Confirm all production account-creation paths support the S22 compatibility guard; older clients may sign in but must not register.
4. Coordinate and verify that all five cohort users' older devices are synced and closed; no remote observer can prove offline drafts were submitted.
5. Owner signs off on a one-account canary, rollback plan, monitoring and release window. Do **not** silently bulk-promote all five.
6. Only with explicit production authorization apply the reviewed SQL and release candidate, migrate one account, validate cloud/device parity, then proceed gradually.
7. Keep legacy rows **read-only for recovery** for a defined retention period. No legacy table deletion during S22.
