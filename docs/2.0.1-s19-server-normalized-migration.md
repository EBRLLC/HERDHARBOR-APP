# S19 — Server-prepared normalized authority and first-login hydration

**Status: candidate code only; production authority NOT changed.**

## Goal
Allow an approved breeder account to enter 2.0.1 with its cloud snapshot already converted to normalized records. Existing S18 `prepareHydration()` then imports normalized records on a clean sign-in, primes the record baseline, and routes future saves through the CAS/outbox writer. The new utility is exclusively an **owner-operated server-side tool**, not a browser feature or an automatic account migration.

## Implemented
- `scripts/s19-cloud-migration-core.cjs` reuses the production v1.8.3 normalizer to build deterministic record plans with SHA-256 plan digests and source checksum parity.
- Only an enabled `internal_test` cohort can be planned. A missing manifest requires **zero** existing rows, but cannot use direct server-side cutover: it must first bootstrap and reconcile through the authenticated S20 login flow. A `dual_write` manifest requires complete row payload/checksum equality and successful normalized reassembly. Other stages fail closed.
- `scripts/s19-cloud-migration.cjs` reads one explicitly identified account via the operator's local PostgreSQL `psql` connection. It defaults to read-only output and never displays animal data.
- Actual execution requires the exact reviewed `--expect-digest`, `--legacy-clients-closed`, an absolute backup directory and a strong `S19_BACKUP_PASSPHRASE` (at least 24 characters). It writes a unique mode-0600 AES-256-GCM encrypted copy containing the original source, manifest and normalized rows; fsync and decryption/readback must pass *before* SQL execution.
- Transaction uses serializable isolation, a per-owner advisory lock, current cohort verification, enabled legacy-write trigger verification, locked legacy row, exact JSON source and timestamp comparison, strict manifest stage/generation checks, zero-orphan checks, readback equality on record payloads/checksums and one transaction for normalized materialization and authority metadata.
- Existing tombstones are retained. Legacy `herdharbor_user_data` and old snapshots are never removed. The existing database trigger blocks outdated legacy writers after normalized promotion.
- CLI reads the completed manifest back and reassembles all records from the server to check postcommit parity before reporting success.

## Deliberate limitations
- **The database cannot know whether an offline 2.0.0 device has unsynchronized in-memory drafts or unsent edits.** `--legacy-clients-closed` is an operator assertion, NOT technical proof. Never execute while any old tabs/PWAs are open or any device has pending edits.
- Source parity is the **last successfully committed cloud snapshot**. It is not proof every device's local dataset has been synchronized.
- Existing S18 client recovery will preserve dirty local data, but a later offline legacy writer cannot rejoin normally after the server's normalized cutover; it must go through recovery/reconciliation.
- S17's already-loaded 2.0.0 eight-second forced reload remains a release blocker. Only release after a tested close/reopen procedure or separately approved bridge.
- The S19 utility uses a direct trusted database connection: it does **not** expose a service-role key or migration RPC to browsers. Keep database secrets, backups and decrypted snapshots outside the repository and artifact pipelines.
- A local encrypted backup is not a substitute for independent off-host backup retention and a rehearsed rollback.
- In contrast with S18 browser-side promotion, the owner-controlled SQL applies equivalent server invariants and direct atomic record materialization/activation rather than running the client three-checkpoint flow. This needs dedicated authenticated RLS, conflict, rollback and two-device acceptance on **nonproduction clones** before real accounts may be approved.

## Commands (operator workstation with PostgreSQL client)
Read-only preflight:
```bash
node scripts/s19-cloud-migration.cjs --account <approved-account-uuid>
```
Once external recovery snapshots, old-client shutdown and preproduction rehearsal have been independently verified, execute a **single** reviewed account using its exact preflight digest:
```bash
S19_BACKUP_PASSPHRASE='<use-a-secret-stored-outside-the-shell-history>' \
node scripts/s19-cloud-migration.cjs \
  --account <approved-account-uuid> --execute \
  --expect-digest <preflight-sha256> \
  --legacy-clients-closed \
  --backup-dir /secure/offsite-backed-up/location
```
Do not embed passwords on command lines or in CI. Prefer loading the backup passphrase from a secret manager without printing it. Standard `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` or a secure service file is used by `psql`.

## Release acceptance (not performed)
1. Confirm exact-head tests, no new code paths used for legacy fallback, Pages publisher setting, cache safety, and S17 old-PWA transition procedure on actual iOS and Android.
2. Validate a restored backup on a nonproduction database. Run read-only preflight on sanitized, representative duplicate-ID/tombstone rabbit/dog/mixed records. Execute there first; verify complete record counts, all attributes, reassembled checksum and normalized-only saves.
3. Test first sign-in on pristine and clean existing browser profiles. Exercise offline/retry, stale account switch A→B→A, CAS conflicts, and rejection of old 2.0.0 full-state writes.
4. For each of five enabled cohort accounts, verify **every old client saved and closed** and independent backup integrity. Cut over one approved account per transaction, read back cloud+device, verify rollback in staging and repeat only when passed.
5. Keep the original legacy record and encrypted recovery copies for a defined retention period. Never drop legacy tables in S19.

**Current production status:** two `dual_write` accounts, three without manifests, none normalized-verified (read-only checked 2026-10-20). No production writes, merges, PWA rollout, or app-store release occurred here.
