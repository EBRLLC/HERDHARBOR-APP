# S18 — Normalized-record primary writer cutover

## Goal and state
The next primary sync engine must use per-record, per-account CAS-protected normalized
writes, not the legacy full `app_state` PATCH. The existing normalized-authority
save implementation in `herdharbor-cloud.js::syncNow()` already routes directly
to `normalizedRollout.syncNormalizedNow()` **after** server-confirmed normalized
authority. S18 creates a guarded path to enter that stage and protects transitional
local storage. It does **not** delete legacy data, change existing customer stages,
alter RLS, or auto-promote live accounts.

Repository: EBRLLC/HERDHARBOR-APP.
Based on draft integration PR #497 at 60cd656987dcabd514ed8bc62dec14fde23848f4.
Branch: `herdharbor-2.0.1/s18-normalized-primary-cutover`.
No merge to main, no deployment, and no production database writes.

## Changes
1. `HerdHarborNormalizedSyncRollout.cutoverToNormalizedPrimary(options)` is an
   **explicit developer/owner-gated operation**. It refuses to proceed unless
   `ownerApproved`, `legacyClientsClosed`, and `backupVerified` are true.
   These client flags are acceptance assertions, **not a secure server-side
   authorization mechanism**; the existing server RLS, cohort and CAS controls
   remain authoritative. It is not called automatically.
2. Requires current authenticated context, server-confirmed `dual_write` stage,
   online/non-syncing status, no cloud conflict, no dirty legacy marker, no pending
   local/outbox mutations. It runs three consecutive real legacy/normalized
   reconciliation checkpoints; aborts on a new local revision; then calls the
   existing `promoteToNormalized()` server-backed authority transition.
3. Post-promotion re-reads manifest stage and verifies the runtime's normalized
   authority status before declaring success. The account's normal save now uses
   the existing record-outbox path, without the legacy full-state PATCH.
4. Hydration now aborts replacing a local workspace if it changed during an
   awaited cloud operation, if the previous state backup failed, or if account
   ownership cannot be written and read back. Includes both normalized and
   legacy hydration; it is necessary to keep existing records safe during cutover.
5. Once a session's stage is known to be `normalized`, a transient eligibility
   failure must **not** send its saves through the legacy writer. Pending work
   remains local with a user-visible error until normalized authority can be
   verified. Leftover legacy dirty state still blocks an unsafe PWA reload.
6. `index.html` and `service-worker.js` load coordinated changed-script
   revisions; offline shell bumped to S18.

## Evidence and limitations
- Nine source-executed targeted S18 regressions passed in an isolated JS test
  harness (cutover approvals, dirty/conflicted/offline state, three verification
  passes, concurrent edit, hydration backup, routing and cache revision).
- `tests/v2.0.1-stabilization-s18-normalized-primary.test.cjs` added to the repo.
- This harness is **not** the complete GitHub Node suite, not live Supabase
  reconciliation, and not real Safari/Android/PWA acceptance.
- At the time of initial analysis, connected production Supabase showed 5 enabled
  cohort accounts, only 2 in `dual_write` with normalized record rows, and 3
  without a manifest/normalized rows. Neither dual-write account had a completed
  normalized verification timestamp. Do not infer all five are ready.
- S17's retroactive 2.0.0 forced-reload issue remains a **release blocker**:
  old already-loaded browser code cannot be patched by this branch. Devices
  must save and close legacy tabs/apps safely before any release is exposed.

## Required release and migration procedure — NOT executed
1. Run complete repository UTC and America/New_York Node suites, security/
   governance tests, monitoring configuration, fingerprinted Pages artifact,
   Android unsigned review bundle and source-unchanged checks at the same head.
2. QA real rabbit/dog mixed farm, separate member accounts, anonymous marketplace,
   local offline edits, outbox retry/rollback, backup restore, paper/photo review
   drafts, pedigree printing and medical/breeding reminders on iOS and Android.
3. Owner-verify backups **outside** the current app's active local state and close
   all older 2.0.0 client windows. Do not clear app storage, purge caches, or
   press Update Now on an unsaved legacy tab.
4. On a nonproduction candidate, confirm a complete normalized read/reassembly
   matches legacy source records/checksums and no old-version writers remain.
   Exercise the explicit cutover operation with acceptance assertions only after
   this verification, then edit, reopen offline, sync, compare and rollback.
5. For each of the three cohort accounts without a manifest, run the separate
   controlled shadow/bootstrap and dual-write progression with full checksums.
   Do **not** force normalized authority or fabricate a manifest.
6. Obtain explicit owner release approval before enabling production authority
   for any account. Promote one eligible account at a time, confirm records on
   two physical devices, then roll out to the next account.
7. Keep legacy tables **read-only recovery material** for a defined rollback
   retention period; removing them now would strand the unmigrated accounts
   and potentially destroy the only recovery copy.

## Pass criteria
- All five authorized accounts have valid, verified normalized records.
- Normalized-authority save never calls `writeCloudRecord`/legacy PATCH.
- A failed normalized RPC leaves the durable outbox pending; a second save
  retries idempotently and cannot overwrite other accounts.
- App startup reads normalized first; failure does not silently hydrate from
  stale legacy records or clear unsaved local work.
- All PR checks green, real-device acceptance signed off, and production
  cutover completed one account at a time.
