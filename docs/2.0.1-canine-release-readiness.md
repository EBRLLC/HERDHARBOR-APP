# HerdHarbor 2.0.1 — Canine Breeding Release Readiness

## Architecture and rollout

The canine workflow uses the existing canonical `animals[]`, `litters[]`, `tasks[]`, health, account-state, pedigree, cloud-normalization, and PWA paths. New cycle, stud, plan, and whelping data is additive optional state. Puppy generation creates canonical Dog animal rows and links them to existing litter rows. No new animal database or Supabase schema was introduced; normalized-primary migration #506 remains reserved for 2.0.2.

The reviewed milestones are intentionally separate:

| Milestone | Scope | State |
| --- | --- | --- |
| PR A #512 | Births/Litters stabilization, transactional local-save boundary, canine core | Draft, unmerged |
| PR B #513 | Heat cycles, mating plans/events, external studs, pregnancy records/estimates, core reminders | Draft, unmerged |

The commits add no migrations. Older clients that replace the entire canonical state may omit unknown new arrays when they save; maintain a verified backup and test mixed-version read/write before rollout.

## Save guarantees

`HerdHarborApp.commitState(next, message)` is the app's current commit boundary. It clones/prepares new canine state and reports success only after the local state store confirms its durable write. It restores the old in-memory state when that local write fails. A successful return is not confirmation that Supabase has acknowledged or synchronized the data. The cloud layer may still be pending or offline.

Same-tab canine editing checks account identity and a snapshot of the relevant cycles, plans, whelpings, litters, and puppy rows before committing. Deterministic litter/puppy IDs make same-state retries idempotent. The current whole-state cloud interface does not expose a per-record compare-and-swap for these arrays, so concurrent writes from independent devices are not proven conflict-free. Do not describe the 2.0.1 workflow as having cross-device atomicity.

## Canine acceptance walkthrough

1. Open an existing female Dog record from Animals and open **Heat cycles & breeding**.
2. Save an observed heat cycle with an unknown stage; close and reopen to confirm its history remains.
3. Create a plan using a same-account male Dog or an account-scoped external stud. Different breeds are supported.
4. Add one or more completed mating events. Keep sire references unknown when the record does not establish a sire.
5. Record laboratory observations and veterinarian-entered interpretations separately. Add ovulation date only when veterinarian-confirmed.
6. Review the estimate's source and range. Breeding-date estimates stay broad; manually supplied and veterinarian-supplied dates remain identified as such.
7. Set pregnancy status and only the reminders the breeder or veterinarian scheduled. A mating does not mark the plan pregnant.
8. Record whelping, counts, delivery method, optional veterinary involvement, and optional owner-entered follow-up dates.
9. Generate or reconcile puppies. Confirm unknown or multiple potential sires remain unresolved; later individual parentage needs an explicit evidence note.
10. Open the shared puppy litter workspace and record weights, health, identity, weaning, dispositions, or losses as known.
11. Save, close, reopen, and confirm records remain in local canonical state. Treat cloud synchronization as pending until the existing sync diagnostics confirm the applicable cloud write.

The automated acceptance path covers state transitions and workspace helpers; it does not replace a real browser/mobile walkthrough.

## Risk register

| Risk | Evidence / impact | Required disposition |
| --- | --- | --- |
| Cross-device lost update | Save API lacks canine-array record CAS; another device may upload an older whole-state snapshot. | Release blocker until a current-architecture mitigation is proven or the owner explicitly accepts the risk. No silent 2.0.2 migration. |
| Older installed client drops unknown arrays | Whole-state serialization by an older client may omit new optional arrays. | Test supported old/new client versions with backup and recovery before rollout. |
| Cloud acknowledgement differs from local save | `commitState` confirms local durable write only. | Keep sync-pending language; run offline/reconnect and cloud diagnostics acceptance. |
| PR CI review | The feature-stack branch filter was corrected; all four stacked PR heads were reviewed through GitHub Actions, including UTC, New York, Android, and pedigree PDF checks. | Continue requiring successful Actions on the exact final head after each additional edit. |
| Clinical interpretation | App stores observations, lab data, and veterinary interpretations without predicting stage or ovulation from elapsed days. | Keep veterinarian-provided values clearly distinguished; do not market estimates as clinical diagnoses. |
| External reference identity | A reference-only sire is an account-scoped canonical `Ancestor Only` animal only when used in puppy lineage. | Keep `ownershipScope: "external_reference"`; never access another member's private animal or imply ownership. |
| Retry after a truly partial older write | Stable IDs reconcile existing puppy rows and refuse unrelated collisions. | Preserve all existing puppy records; inspect and reconcile before retry. Cross-device races remain separately unresolved. |
| PWA update with new fields | Service worker keeps the previous shell until its existing unsaved-work readiness gate allows activation. | Confirm older-client behavior and preserve backups; code rollback does not undo or delete new records. |

## Rollback and recovery

1. Stop rollout and retain the last verified production commit.
2. Preserve canonical Dog, litter, task, cycle, plan, whelping, health, and puppy records; do not delete them to revert code.
3. Revert the release code and retain account backups before any old-client write.
4. If a local save failed, retry from the pending editor; the transaction's prepared state was not applied. If an uncertain/partial old snapshot exists, reconcile deterministic puppy IDs against `sourceBirthId` and `birthOrder` before regenerating.
5. After connectivity returns, inspect existing cloud sync diagnostics and verify the canine arrays and relationships on the destination account before declaring synchronization complete.
6. Do not edit production Supabase data as part of test recovery. No production data was changed during this work.

## Additional 2.0.1 canine-specific release safety review (October 27, 2026)

- Editing a whelping must **preserve manually completed reminders** when their title/due date is unchanged. An explicit reschedule reopens only the changed reminder. Removed reminders are identified separately so re-adding them does not create duplicates or misrepresent a manually completed reminder.
- Selecting an existing whelping must reload its custom follow-up title/date alongside birth and count fields; selecting an unrecorded plan resets those fields rather than copying values from another litter. Generic litter follow-up metadata must not be silently blanked by a canine edit.
- A plan whose litter has already been recorded must not be silently reverted to an active breeding or cancelled through generic mating/pregnancy forms. Its linked birth and puppy history remains immutable through those transitions.
- Regression tests cover completed reminder retention, explicit rescheduling, removed/re-added reminders, edit-form restoration/clearing, follow-up preservation, and whelped-plan status protections.
- The PWA shell includes updated versioned canine breeding/whelping scripts and a new cache identity. This prevents the revised form being mistaken for the old shell, but does not replace a real-device upgrade acceptance pass.

**Remaining release gate:** Do not confuse code-level tests with physical iOS/Android validation. Confirm on test devices that a user can create/edit/reopen a cycle, planned/actual mating, pregnancy estimate, whelping, and puppy records; that other species are unchanged; and that an old installed PWA upgrades without losing unsynced local edits. Do not clear storage or migrate production data to perform these tests. Existing legacy-cloud overwrite behavior belongs to separate 2.0.2 PR #506.
