# HerdHarbor 2.0.1 — Canine Whelping and Puppy Records (PR C)

## Data model

All records are additive optional fields in the existing canonical account state. No Supabase schema change, data migration, normalized-primary cloud cutover, or production database write is included.

- `canineWhelpings[]`: stable ID `canine_whelping_<planId>`, linked `planId`, `cycleId`, `damId`, optional established `sireRef`, linked `litterId`, date/time, delivery method, veterinary involvement, notes, and deterministic puppy-generation operation ID.
- `litters[]`: existing shared litter row with `species: "Dog"`, `canineWhelping: true`, `canineWhelpingId`, existing count and notes fields, and `offspringIds`. Rabbit litter rows and their behavior remain unchanged.
- `animals[]`: canonical Dog rows with stable ID `canine_puppy_<whelpingId>_<birthOrder>`, `sourceBirthId`, `litterId`, `birthOrder`, unknown sex until entered, dam, and an explicit `canineParentage` reference/status. The existing pedigree validator checks known relationships. Unknown or multiple potential sires stay unresolved. An unlinked external stud is represented only as a same-account canonical `Ancestor Only` reference with `ownershipScope: "external_reference"`; it is not represented as an owned operational animal.
- `tasks[]`: deterministic canine whelping task IDs for a breeder-entered custom follow-up and breeder-entered expected-weaning reminder. Updating or clearing those dates updates/completes only those exact linked tasks. There are no universal medical schedules.
- Dog puppy identity may add `breed` and `canine.coatMarkings` through the existing shared litter workspace. Weight and health entries use the existing canonical health records and workspace functions.

No AKC, UKC, or other registry status is inferred or assigned to puppies. External stud registration/title strings remain owner-entered metadata. HerdHarbor lineage output remains internal recordkeeping and is not registry-issued documentation.

## Validation and retry behavior

Whelping validation requires a same-account female Dog, a saved plan with at least one completed-mating event, non-cancelled plan, valid calendar date/time and delivery method, nonnegative integer counts, and neonatal losses no greater than born-alive count. Generic Births/Litters forms may adjust supported totals and notes but cannot change a canine whelping's date, dam, sire, or plan link, and cannot delete its linked record.

Puppy generation works on a cloned state. Stable IDs derived from whelping and birth order make a repeated operation reconcile existing rows rather than add duplicates. It refuses ID collisions with unrelated records and preserves puppy rows if a count is later corrected downward. The local state-store commit boundary is the only point that applies the resulting state; a failed commit retains the prior live state. Stable IDs protect retries over the same canonical state, but without server-side compare-and-swap they cannot prevent an older independent device snapshot from replacing a newer one.

The UI calls the existing `HerdHarborApp.commitState` API. A true return confirms a successful local durable state-store commit only. It does not confirm Supabase/cloud acknowledgement or cross-device visibility. Offline pending edits rely on the existing app sync path; PR C adds no alternate queue, conflict resolution, or cloud schema.

## Puppy development integration

Puppy rows can be generated before names, sex, coat, weight, or health details are known. The linked shared Manage Litter workspace supports individual and bulk weights, health entries, dog breed/color/markings, and existing litter development actions. Breeder-entered reminders remain explicit. Existing rabbit identity and litter behavior are covered by regression tests and are not changed by Dog-only fields.

## PWA and rollback

The canine whelping workspace is part of the required offline shell. The service-worker cache identity changes to install a fresh immutable asset set; the prior cache remains governed by existing update readiness checks. Market analytics moves from install-blocking shell precache to runtime network-first caching so the required shell stays within its established 50-asset bound; the script remains in `index.html`, and its normal online load is cached for later offline use.

Rollback is a code-only revert of PR C while preserving the canonical data. New `canineWhelpings[]` records and Dog puppy rows may not be understood or preserved by older whole-state clients, so code rollback alone is not sufficient once new records exist. Before production exposure, retain a verified account backup and confirm old/new client read-write compatibility. Do not delete new records as a rollback step. No production account data was used for testing.

## Not yet release-proven

The automated tests exercise deterministic generation, retries, collision refusal, external reference handling, unknown/multiple parentage, lineage validation, dog/rabbit isolation, and shared litter development helpers. They do not prove multi-device atomicity, real mobile-browser behavior, cloud synchronization, or every PWA reload/reconnect path. Those remain PR D acceptance and release blockers.
