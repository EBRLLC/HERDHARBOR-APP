## Gate B — controlled tester deployment prerequisites

1. Obtain explicit owner approval for the exact SHA, deployment time, production schema migration, staged canary order, and acceptable rollback posture. Merging alone is **not** deployment approval.
2. Freeze relevant writer/schema changes. Confirm production account inventory **read-only** immediately before release:

```sql
SELECT
  (SELECT count(*) FROM auth.users) AS auth_accounts,
  (SELECT count(*) FROM public.herdharbor_user_data) AS legacy_snapshots,
  (SELECT count(*) FROM public.herdharbor_sync_manifest WHERE cutover_stage='dual_write') AS dual_write,
  (SELECT count(*) FROM public.herdharbor_sync_manifest WHERE cutover_stage='normalized') AS normalized,
  (SELECT count(*) FROM auth.users u WHERE NOT EXISTS (
     SELECT 1 FROM public.herdharbor_user_data d WHERE d.user_id=u.id
   ) AND NOT EXISTS (
     SELECT 1 FROM public.herdharbor_sync_manifest m WHERE m.user_id=u.id
   )) AS auth_only;
```

3. Independently export encrypted backups for **every** existing cloud account and the schema/auth/linked application dependencies needed for restoration; record immutable backup identifiers, per-account version/generation, tombstone count and record checksums. Restore copies to isolated infrastructure and verify authorized data readback before proceeding. A locally decrypted archive alone is not an operational recovery guarantee.
4. Account for local-only drafts separately. An offline device cannot be checked remotely; do not promote its account or clear its browser storage until that account signs in and available local state is examined. If the correct source of truth is ambiguous, hold and obtain an explicit user choice after preserving both sources.
5. Review and approve the exact production DDL sequence **without** automatically executing it on merge. Staging dependency order: normalized foundation; legacy guard; RLS; record CAS; cohort; **group CAS before authority cutover**; conflict wrappers; normalized-only signup trigger; **`v2.0.2-normalized-recovery-rollback-guard.sql` after the authority function**. Confirm each script's guards, repeat behavior and permissions; fail closed on any migration error.
6. Verify Pages source remains GitHub Actions (not raw branch publishing), release artifact hash/build identity equals the approved SHA, staging keys are absent from production assets and all secrets remain in protected environments. Do not publish an app requiring DDL before the compatible schema is verified.
7. Enable and observe Supabase Auth error, denied RLS, CAS conflict, failed normalized save, stale-client upgrade and PWA asset identity telemetry, plus database availability, backup completion and checksum reconciliation.
8. Start with one owner-approved existing tester canary, then expand only after correct authenticated record readback and a successful save across logout/login. Do not force the five Auth-only accounts through empty initialization; reconcile from their own devices individually at login.

## Objective stop conditions

**Stop and hold all promotions immediately** on any one of: a cross-account read/write or wrong-owner local workspace, confirmed lost animal/litter/medical/pedigree data, mismatch between backup and restored records, unverified backup, skipped schema dependency, normalized authority without checked reconciliation, unauthorized legacy overwrite, failed authorization enforcement, failed data integrity checksum, untracked restored duplicate, or automatic unexpected production publication. These are zero-tolerance critical incidents.

**Pause canary expansion** on any irreconcilable CAS conflict, a repeatable normalized save failure, recurring HTTP authentication failure in a known-valid synthetic/tester session, repeated PWA stale-client errors, or unexpected failed startup. Treat three unexplained failed authenticated logins in a 15-minute controlled canary as an operational investigation threshold, not as permission to proceed when fewer errors cause data-integrity concerns.

Automated protections: RLS/owner-scoped RPCs, generation CAS, record-version CAS, outbox preservation, stale-client legacy write guard, first-login unknown-cloud hold, encrypted backup integrity verification, release SHA check, GitHub Actions test gates. Operator actions: secure off-host backups, isolated restore/readback, inventory reconciliation, owner approval, canary sequencing, incident freeze, account-specific conflict/source-of-truth review, and actual rollback approval.

## Recovery decisions

| Failure class | Decision | Prohibited shortcut |
|---|---|---|
| Frontend regression, server schema compatible | Pause publication; redeploy last compatible reviewed frontend after verifying service-worker and offline data retention | Reverting schema/data alongside frontend without parity check |
| Normalized writes succeeded but migration must be reversed | Freeze writes; export newest normalized generation and reconstruct/reconcile the target snapshot in isolated staging, then authorize a tested account-specific recovery | Downgrading authority to an older legacy snapshot and discarding normalized records |
| Database corruption or outage | Restore independent verified database backup to isolated environment, validate RLS/auth/schema/application reads, then separately approve production recovery | Assuming that an encrypted archive's successful decrypt restores every application dependency |
| Individual Auth-only or dual-write account mismatch | Preserve both local and cloud sources; verify ownership, version and checksums; require explicit user choice when ambiguous; proceed through supported CAS/migration path only after validation | Treating an absent manifest as proof of no animal records |
| New normalized-only signup | Restore normalized backup while retaining normalized authority | Attempting unsupported rollback to non-existent legacy snapshot |

Legacy recovery material must remain retained; never automatically delete or replace it. Every recovery needs before/after record counts, checksums, relationships and tombstone/record generation validation. An interrupted recovery must be idempotently resumed or held, never retried blindly.

## S24 recovery guard acceptance (staging only)

- The source migration `supabase/v2.0.2-normalized-recovery-rollback-guard.sql` was installed **only** in synthetic Supabase staging as `herdharbor_202_normalized_recovery_rollback_guard`. There has been no production SQL execution.
- Independent staging `BEGIN / ROLLBACK` fixture tests (no persistent account mutation) verified that a normalized-to-dual-write downgrade **fails** without a recovery lock, **fails** when normalized records were updated after the stated materialization timestamp, and **permits** a fresh materialized legacy row. The existing S20 normalized-only signup guard separately rejects every legacy rollback for normalized-only signups.
- The staging trigger verifies **materialization freshness**; it does **not** establish that operator-supplied recovery JSON equals all current normalized records. An independent parity proof remains mandatory before any production rollback. This is a recovery-operation gate, not authorization to reverse authority on production.
- CI includes a disposable PostgreSQL 17 test for these failure modes, in addition to separate encrypted backup / restore verification. A failing or incomplete exact-head CI remains a merge blocker.
