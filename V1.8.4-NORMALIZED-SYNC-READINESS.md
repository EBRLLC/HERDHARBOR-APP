# HerdHarbor v1.8.4 Normalized Sync Production Readiness

## Authority

This phase validates readiness of the normalized-sync architecture already present in v1.8.3. It does not enable unrestricted normalized production authority.

Persisted stages remain:

`legacy -> shadow -> dual_write -> normalized`

Rollback remains adjacent and reversible:

`normalized -> dual_write -> shadow -> legacy`

Legacy full-state data remains the recovery path.

## Required operator sequence

1. Confirm current application release identity and cloud telemetry availability.
2. Apply `supabase/v1.8.3-cloud-sync-normalized-records.sql` through the authorized database change procedure.
3. Apply `supabase/v1.8.3-cloud-sync-cutover-legacy-guard.sql`.
4. Run the read-only `supabase/v1.8.3-cloud-sync-rollout-preflight.sql`.
5. Stop if any required table, RLS policy, RPC, or stale-client guard is missing.
6. Start only with an explicit internal allowlist cohort.
7. Promote one adjacent stage at a time only after required verification/reconciliation evidence exists.
8. Preserve legacy rollback data; do not perform destructive cleanup in v1.8.4.

## Readiness evidence contract

Before `legacy -> shadow`:
- normalized records and manifest tables exist
- RLS is enabled
- owner-only read policies are present
- direct authenticated mutation is revoked
- batch, verification, stage-transition, and guarded-writer RPCs exist
- stale legacy-client write guard is installed and enabled
- monitoring and rollback paths are available
- account is explicitly cohort-eligible

Before `shadow -> dual_write`:
- bootstrap completed or resumed idempotently
- current verification exists
- source and verified checksums agree
- verified and normalized record counts agree
- reconciliation shows zero unresolved divergence
- no bootstrap failures remain

Before `dual_write -> normalized`:
- legacy saves remain authoritative and healthy
- normalized write degradation does not convert legacy success into data loss
- normalized-read validation shows no fallback during the acceptance window
- guarded writer preparation succeeds
- current verification remains valid
- rollback remains available

## Failure and rollback requirements

- Schema/preflight failure: stop.
- Shadow bootstrap failure: retain legacy authority and resume only through the gated bootstrap.
- Reconciliation mismatch: block promotion.
- Dual-write normalized failure: keep the successful legacy save authoritative and record safe failure evidence.
- Normalized-read fallback: block final promotion or expansion.
- Rollback failure: release blocker.
- Rollback clears/requires re-establishment of verification and writer readiness before re-promotion.

## Production boundary

This phase does not:
- add rollout-control modules to unrestricted production startup
- enable percentage cohorts
- mass-enable normalized sync
- delete `herdharbor_user_data`
- change promotion thresholds to satisfy tests
- perform schema application automatically
