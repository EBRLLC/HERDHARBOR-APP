# HerdHarbor 2.0.0 Production Release Contract

## Purpose

HerdHarbor 2.0.0 promotes the current application to a stable production release while preserving the hardened data, account, sync, billing, update, and monitoring protections established during the 1.8.x release line.

The product is a farm management application with specialized depth in rabbit management.

## Release boundaries

The 2.0.0 promotion must not:

- delete or reset canonical user data
- weaken row-level security or account-boundary protections
- create a second persistence or sync path
- automatically expand normalized-sync production cohorts
- remove retained cloud recovery data
- change Founder eligibility or subscription pricing unintentionally
- rename stable component files solely to match the whole-app version
- expose hidden AI capabilities solely because the application version changed
- weaken tests to make the release pass

Historical release notes and historical component versions remain valid historical records.

## Production capability contract

The stable application must preserve working support for:

1. farm and animal records
2. rabbit-specialized breeding and litter workflows
3. pedigree records and guided pedigree workflows
4. genetics tools and stored prediction evidence
5. health records and health insights
6. tasks and recurring work
7. sales and customer records
8. production, budget, profitability, analytics, and reporting
9. authenticated cloud sync, offline recovery, conflict handling, and cross-device use
10. account isolation during sign-in, sign-out, reload, and account switching
11. Member, Founder, Junior, referral, credit, checkout, webhook, payment-ledger, and billing-portal behavior
12. installable PWA behavior
13. Android package generation
14. production monitoring with original failure provenance preserved

## Cloud-sync authority

Normalized-sync authority remains controlled by the existing rollout policy. The application version bump does not change an account's sync stage.

Required invariants:

- legacy full-state recovery remains retained unless an explicitly reviewed rollout says otherwise
- normalized writer/read authority remains gated by existing readiness controls
- adjacent rollback remains available
- conflicts must fail safely rather than silently overwriting another device
- ordinary users must not be required to clear local browser data as normal recovery behavior

## AI capability inventory

### Paper Pedigree photo reading

Status: production-deployed and production-hardened, but controlled-access for the AI read action.

Required behavior:

- authenticated server-side provider call
- provider credentials remain server-side
- bounded provider timeout
- structured output validation fails closed
- uncertain fields remain uncertain rather than guessed
- explicit human review and confirmation before canonical commit
- duplicate and conflict protection
- aggregate-only operational metrics
- usage-limit enforcement
- standard accounts do not gain the hidden AI read action solely from the 2.0.0 release

Multi-photo pedigree merging remains deferred.

### Voice-assisted entry

Status: production-deployed, controlled-access.

Required behavior:

- no direct canonical persistence
- creates a review draft only
- canonical Health/Breeding forms remain final save owners
- ambiguous or incomplete instructions remain unresolved for user review
- telemetry excludes transcript and farm-record payload content

### Photo-assisted entry

Status: production-deployed, controlled-access.

Required behavior:

- authenticated server-side extraction
- no provider credentials in browser code
- no direct canonical persistence
- explicit user review/selection before handoff
- unsupported or incomplete input fails closed
- canonical Animal/Health forms remain final save owners
- telemetry remains coarse metadata only

### AI image usage controls

Status: production infrastructure enabled.

The existing per-user and global quota protections remain authoritative. Usage ledgers must not store source images, prompts, provider responses, or extracted farm content.

## Product-language contract

Normal member-facing surfaces must not expose:

- Alpha or Beta release branding
- tester/test-build language
- internal engine/runtime/module/adapter version numbers
- internal rollout/cohort/migration terminology where it is not necessary to the user's action
- build IDs

The whole application version may appear in Settings/About as `Version 2.0.0` for support.

Admin-only or developer diagnostics may retain technical metadata when it is necessary for troubleshooting and is not presented as normal product branding.

## Stacked release ancestry

This release is implemented as a dependency stack.

- Phase 1 branches from the reviewed current `main`.
- Every later phase branches from the final reviewed head of the immediately previous phase.
- If an earlier phase is corrected, dependent phases must be rebuilt/rebased onto that corrected head before they are treated as valid.
- No red phase may be treated as a valid base.
- No phase is auto-merged merely to start the next phase.

## Release blockers

The final 2.0.0 release is NO-GO if any of the following remain:

- unresolved data loss, silent deletion, or stale overwrite
- wrong-account local/cloud state hydration
- unresolved cross-device conflict behavior
- broken PWA update path or stale release assets
- authentication/session regression
- billing state that can destructively downgrade stored records
- Founder pricing exposed to ineligible accounts
- referral/credit duplication or loss
- hidden AI becoming public unintentionally
- monitoring that replaces original provider/runtime error provenance
- failing required security, regression, state-integrity, billing, PWA, monitoring, or Android checks

## Rollback requirements

- application changes: revert the owning phase without deleting canonical user data
- sync: preserve adjacent rollback and retained recovery data
- PWA: preserve deterministic old-cache retirement and a valid prior shell path
- auth/account boundaries: restore last-known-good behavior without cross-account hydration
- subscriptions: restore last-known-good entitlement behavior without deleting farm records
- hidden AI: disable availability without changing canonical records already reviewed and saved

## Completion criteria

The release contract is satisfied only after the later release phases verify the formal 2.0.0 test gate, PWA cutover, Android package, billing, sync/account boundaries, AI behavior, public positioning, current release workflows, monitoring identity, store/release material, and final production acceptance.
